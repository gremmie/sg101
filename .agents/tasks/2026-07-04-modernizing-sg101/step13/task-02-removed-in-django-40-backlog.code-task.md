# Task: Clear the RemovedInDjango40 Backlog While Still on 3.2

## Description
Replace the APIs Django 4.0 removes, and delete the inert `from __future__`
lines, **before** starting the 4.0 rung — while every one of these is still a
warning rather than an error.

Doing this on 3.2 means each replacement can be verified against a green suite
in isolation. Doing it during the 4.0 rung would pool it with 4.0's own breakers
and make a failure ambiguous.

## Background
Step 10 deferred this backlog explicitly when it landed Django 3.2. The
inventory below was **re-counted against the tree on 2026-08-03**, and two of
the plan's numbers were wrong in ways that matter:

| Item | Plan said | Actual | Note |
|---|---|---|---|
| `ifequal` / `ifnotequal` | 17 | **17** ✅ | 6 template files |
| `request.is_ajax()` | 7 | **4** | see below |
| `Signal(providing_args=…)` | 3 | **2** | both in `forums/signals.py` |
| `force_text` | 2 | **2** ✅ | `core/markup.py:6,27` |
| `urlquote` | 2 | **2** ✅ | `messages/templatetags/messages_tags.py:7,31` |
| `ugettext_lazy` | 1 | **1** ✅ | `elsewhere/models.py:8` |
| `from __future__` | 32 | **32** ✅ | 16 of them are migrations |

**The `is_ajax` count was inflated by a name collision.** Seven lines match the
string, but three of them are in `forums/templatetags/forum_tags.py` (lines 117
and 125), where `is_ajax` is a **parameter name on the `show_form` tag** and has
nothing to do with the removed `HttpRequest` method. Renaming or "fixing" those
would be a pointless edit to working code. The four real call sites are:

- `core/middleware.py:49`
- `user_photos/views.py:64`, `:103`, `:219`

The replacement is `request.headers.get('x-requested-with') ==
'XMLHttpRequest'`. **This is not a pure refactor** — `is_ajax()` was removed
because it only ever detected jQuery-style requests, and the site's own JS is
what sets that header. Confirm the site's JS actually sends it on each of those
four paths before assuming the replacement is equivalent; `user_photos/views.py`
guards three POST endpoints with it, so a wrong answer there breaks uploads
rather than degrading gracefully.

**`django.conf.urls.url` is a non-issue here.** The plan lists it as a 4.0 rung
concern, but the tree has **zero** usages — the single `conf.urls` import is
`from django.conf.urls.static import static` at `sg101/urls.py:1`, which was
never removed. 89 modules already import from `django.urls`. Nothing to do.

**The 32 `from __future__` lines split 16/16.** Sixteen are in migration files
(`forums`, `comments`, `countdown`, `news`, `downloads`) — auto-generated by
Django 1.x and never touched since. They are inert on Python 3 and editing them
is safe, but it is churn across historical files. Decide deliberately whether
migrations are in scope and say which way in the commit message; do not leave it
ambiguous.

**`core/markup.py` appears in two tasks.** Its `force_text` import is here;
its per-call `Markdown` construction is task 08. Expect to touch the file twice,
and do not smuggle task 08's change into this one.

## Technical Requirements
1. Replace 17 `ifequal`/`ifnotequal` tags with `{% if %}`/`{% elif %}` across
   the 6 template files: `sg101/templates/forums/pagination.html`,
   `core/pagination.html`, `core/pagination_query.html`,
   `ygroup/pagination.html`, `shoutbox/shout_detail.html`,
   `downloads/download_list.html`.
2. Replace the **4** real `request.is_ajax()` calls with a header check, and
   **verify the client actually sends the header** on each path rather than
   assuming. Leave `forum_tags.py`'s parameter of the same name alone.
3. Remove `providing_args` from the two `django.dispatch.Signal(...)` calls in
   `forums/signals.py` (lines 13 and 20). The argument was documentation-only;
   the signals themselves are unchanged.
4. Replace `force_text` with `force_str` (`core/markup.py:6,27`), `urlquote`
   with `urllib.parse.quote` (`messages/templatetags/messages_tags.py:7,31`),
   and `ugettext_lazy` with `gettext_lazy` (`elsewhere/models.py:8`).
5. Delete the inert `from __future__` imports, stating explicitly whether the 16
   migration files are included.
6. **The suite must be green after each category**, not only at the end. These
   are independent changes and should fail independently.
7. Add or extend tests where a replacement is behavioral rather than textual —
   specifically the four AJAX guards, which are access-control checks on POST
   endpoints, not cosmetics.

## Implementation Approach
1. Start with the template `ifequal` sweep — the largest count, the lowest risk,
   and entirely mechanical. Verify pagination rendering, since 4 of the 6 files
   are paginators.
2. Do `providing_args`, `force_text`, `urlquote` and `ugettext_lazy` next:
   seven lines total, all pure renames.
3. Do `is_ajax` last and carefully. Read the JS that calls each endpoint before
   editing the guard, and write a test that fails against a request without the
   header.
4. Sweep `from __future__` once the behavioral work is done and verified, so the
   churn does not obscure anything.
5. Confirm no `RemovedInDjango40Warning` remains: run the suite with
   `-W error::DeprecationWarning` or equivalent and record what is left.

## Acceptance Criteria

1. **No RemovedInDjango40 APIs Remain**
   - Given the completed sweep
   - When the tree is searched for `ifequal`, `request.is_ajax`,
     `providing_args`, `force_text`, `urlquote` and `ugettext`
   - Then the only remaining match is `forum_tags.py`'s `is_ajax` parameter,
     which is unrelated to the removed method

2. **Deprecation Warnings Are Silent**
   - Given Django 3.2.25
   - When the suite runs with `RemovedInDjango40Warning` promoted to an error
   - Then no test fails on a warning from application code

3. **AJAX Guards Still Guard**
   - Given the three `user_photos` POST endpoints and the `core` middleware
   - When a request arrives without the `X-Requested-With` header
   - Then it is rejected exactly as it was before the change, proven by a test
     that fails if the guard is removed

4. **AJAX Guards Still Admit Real Traffic**
   - Given the site's own JavaScript for photo upload
   - When it posts to each converted endpoint
   - Then the request is accepted — verified against the actual client code,
     not assumed from the header name

5. **Pagination Renders Unchanged**
   - Given the four converted paginator templates
   - When a paginated forum, ygroup, downloads and core view is rendered
   - Then output is identical to before the `ifequal` conversion

6. **Signals Still Fire**
   - Given `forums/signals.py` with `providing_args` removed
   - When a topic and a post are created
   - Then `topic_content_update` and `post_content_update` receivers run with
     the same `created` argument as before

7. **Suite Green**
   - Given the completed task
   - When the suite runs with `--settings=sg101.settings.docker_test`
   - Then all 798 tests pass and `check` is clean
